# R003：合成データ・回帰・研究受入テスト

作成日：2026-09-13 / 状態：**実装時の受入仕様。プロジェクトのテストは未実施。**

## 1. 判定の原則

実データで利益が出ることをソフトウェアの正しさの証拠にしない。特徴量、イベント時刻、約定、費用、期間アクセス、保存、評価を合成データで検証する。前回の44件通過という会話記録を、R003を追加した後のテスト通過と読み替えない。

「実装受入」と「研究上の候補判定」は別である。正しく実装され、全ソフトウェアテストが通っても、期待値が負なら研究判断はREJECTとなる。

## 3. 先読み防止・prefix不変性

| ID | 操作 | 必須の期待結果 |
|---|---|---|
| C01 | cutoff以後の全価格を変更し、未来セッションを追加 | cutoffまでに利用可能な特徴量とsignalは完全一致 |
| C02 | 現在セッションの30分以後の価格を変更 | 過去中央値と当該初動のU/D/R/qは完全一致 |
| C03 | 現在初動を計算する前に履歴更新する誤実装を注入 | Mに現在値が混ざるためテスト失敗 |
| C04 | cutoff直後の最初のopenだけ変更 | cutoff以前に完了した取引は一致。cutoff時点のpending注文の将来fillは変わってよい |
| C05 | full-runと過去prefix-runを比較 | 同じ時点までのシグナル・完了取引・履歴hashが一致 |
| C06 | 同じtrade_dateのNight/Day、年境界を含める | session順は実時刻。historyのavailable_atが現在開始を超えない |
| C07 | セッション後半の品質ラベルを変更 | それ以前の売買可否は変わらない |
| C08 | キャッシュのdata/calendar/期間hashを変更 | キャッシュ不一致を拒否、再計算。全期間キャッシュを誤利用しない |

future変更テストで将来のexitまで不変であることは要求しない。まだ観測していない価格で決まるfill/exitまで固定すると、逆に不自然な実装を許してしまう。

| E13 | entry 1分遅延、次バーでレンジ内へ戻る | 元の方向を固定した遅延注文。再ブレイク条件を追加しない |
| E14 | exit 1分遅延で有利価格になる | 改善をそのまま報告。不利overlayと混同しない |
| E15 | has_positionの立ち上がりとfillバーを照合 | 通常/欠損/遅延で実fill時刻を正確に特定できる |
| E16 | エンジン強制フラット・END_OF_DATAを発生 | 取引を落とさず、異常件数と候補阻止を記録 |

時刻契約の具体例：開場08:45、初動終了09:15、09:15開始バーでブレイクなら通常entry09:16。H=60のexit予定10:16、決済指示は10:15開始バーの確定終値。バーラベルが終値時刻の基盤ではアダプターを通し、同じ経済的タイミングを再現する。

## 5. コストと台帳照合

以下はtick=5ポイント、倍率100円、片道手数料30円という設定に対する合成算術テストである。

| P02 | 同じreference、片道2 tick | 実fill=40,010/40,020、gross=1,000円、net=940円 |
| P03 | ショート entry=40,000、exit=39,970、片道1 tick | 実fill=39,995/39,975、gross=2,000円、net=1,940円 |

注文価格ではなく実fillとreferenceの対応を確認する。手数料2倍を「往復30→60」と誤解しない。基準は往復60円、2倍は往復120円。

## 10. ソフトウェア受入の完了

R003仕様に対応する合成テストと重要な既存回帰を実行し、Ruff・mypy・関連pytestの実際の結果を記録する。テスト総数は、実装後に収集された値を使用する。

最低限の受入条件は、上表の因果性/時刻/費用/期間保護/対照一致/保存保護が満たされること、旧研究が意図せず変わらないこと、READMEの実行例が実装済みCLIと一致すること。

実データ研究まで実施する依頼の場合は、品質ゲートに従った実験、全ゲートのbooleanと根拠、NOT_EVALUATEDのOOS、未参照のFinal Holdoutを含め、再現可能な最終報告を保存する。品質により停止した場合も、未実行項目を明確にする。
