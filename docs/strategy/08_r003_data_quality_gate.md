## RG-20260915-01: 品質ゲートの現在の適用

下段はR003監査の原案であり、冒頭の「実データの監査は未実施」は原案作成時点の記述である。後続の [研究結果](04_research_results.md)に価格来歴・roll・隔離・出来高監査の報告が存在する。本改訂ではそれらを実データで再監査していない。

### 継承する要件

原案の「後半の異常で過去の主成績を除外しない」「roll unknownとfalseを分ける」「価格を丸めない」「新データ版にする」「OOS/2026を閉じる」を今後の全研究にも適用する。R004の事後whole-session隔離は旧再現用ビューとして保持し、当時のE_execへ混入させない。

### 追加の監査単位

|監査|必須証拠|不合格・未確認時|
|---|---|---|
|時刻の意味|bar-start/end/auction、interval、利用可能時刻・訂正方針|時刻境界を使うPnLは停止|
|品質のas-of|quality_available_atとdetected_at、前後の選別差分|主集合の因果性監査待ち|
|U独立性|初動など入力窓だけで構成。response/entry/exit不要|再帰的history不成立や未来選別を修復|
|E_execとE_analysis|判断時点と結果観測の別台帳|主実行成績として利用不可|
|既約定後の欠測|注文と建玉を保持、未知損益null|完全な主Net/CIと候補昇格を停止|
|source semantics|対象ファイルの価格・volume・roll/adjustment証拠|利用目的別にBLOCKED/PASS_LIMITEDを維持|

全当該sessionを先に除外したビューだけで行うprefixテストでは、集合選択の先読みを検出できない可能性がある。loaderとQCを含む元の入力からfuture mutationをかけ、U・E_exec・orderまで比較する。未来のfillやexit価格まで一致させる必要はない。

### 目的に応じた完了

BLOCKEDでも、原因と次に必要な証拠が確定すれば監査runは完了できる。ただし「監査完了」を「品質PASS」としない。実データ監査はDevelopmentに対応する行だけに限定し、外部資料確認だけで実限月執行可能性を証明したことにしない。

原案のPASS_LIMITEDは説明可能な限定研究範囲を意味する。重大なbar時刻／価格意味の不明を残す研究のPnLは停止する。修復後の品質分類は証拠で決め、文書更新では昇格させない。仕様確認のための問い合わせ・購入・データ取得は別の明示依頼と権限に従う。

# R003：価格・roll-risk・期間アクセスの品質ゲート

作成日：2026-09-13 / 状態：**監査仕様。実データの監査は未実施。**

## 1. 目的

R003の損益を見る前に、過去20回の初動幅を比較できる価格系列か、5ポイント刻みの約定想定と整合するか、連続系列切替の影響を説明できるかを確認する。価格の丸め、都合の悪い月の除外、raw/Goldの上書きで成績を整えない。

共有された前回報告には、完全一致の年次重複5,197時刻、`MISSING_PREV_EXPECTED` 244本、`STATISTICAL_PRICE_JUMP` 303本、`TICK_GRID_VIOLATION` 1,221本、代表点の `roll_risk` が全件falseという記録がある。これらは監査対象を定めるための**前回記録**であり、今回の再集計結果ではない。

## 2. 読み込み境界

監査対象はDevelopmentの正規化済み入力と、その行に対応する出所だけ。期間の判定は `trade_date`。2025年後半・2026年以降の価格、損益、特徴量、品質集計を開かない。

最初にパーティションを限定し、その後にtrade_dateを検査する。2025年7月のファイルに混在する6月末など、calendar_dateとtrade_dateの差が生じる配置を想定し、manifestの期間メタデータと既存データ契約で対応範囲を確かめる。単にディレクトリ名の年月だけでOOS/Developmentの全行を区別できるとは仮定しない。

対象パーティションにOOS行が同居する場合は、価格を実体化する前にtrade_dateで抽出する。列選択・フィルタ条件・実際に返した行の最大trade_dateをログに残す。物理ストレージの圧縮ブロック単位I/Oと、研究者・戦略へ価格を返すアクセスは区別して記録する。2026年パーティションは列挙段階で拒否する。

rawの照合では、Development行の `source_file / source_row_number` に対応する価格セルだけを読む。2025年の年次ファイルを丸ごとDataFrame化してから後半を捨てる手順は使わない。対象行だけの取得を保証できない場合は、その読み取り方式を修正するまでraw照合を停止する。2026年rawは開かない。

ファイル名や予定カレンダー日時のメタデータを扱うことと、ホールドアウト価格を分析することは同一ではない。ただし出所不明の全期間特徴量キャッシュを流用しない。

## 3. Tick-grid監査

JPXの通常の立会市場では日経225miniの呼値は5ポイント。制度概要にはJ-NETの別の呼値単位も記載されているため、5で割り切れない値を見ただけで「誤データ」と断定しない。市場区分・価格種別・連続系列加工の有無を確認する。[S1]

### 取得する証跡

1行ごとに時刻、trade_date、session、source、OHLCの各剰余、volume、適格性、品質フラグを記録する。raw値→型変換→正規化→Goldの変換経路を追い、元データに存在した値か、変換によって生じた値かを分類する。

年、月、source、時刻帯、OHLC列別に発生件数を集計する。同一バーで複数価格が違反しても、バー件数と価格セル件数を混同しない。

### 確認する原因候補

| 分類 | 確認内容 | 取扱い |
|---|---|---|
| 取り込みバグ | 桁、整数化、列ずれ、日時の対応、異なる商品混入 | 修正前後を保存し、データ版を更新。損益前に仕様を再凍結 |
| 連続系列の調整 | 加算・比率調整、調整の適用単位、バー内/セッション内の一貫性 | 加工根拠とPnL・レンジへの影響を分けて記録 |
| 通常立会以外の価格 | 清算値、別市場の約定、集計値等 | 売買可能なOHLCかを供給仕様で確認 |
| 原因不明 | 出所または変換が説明できない | 実データPnLを停止 |

一定の加算値aが1セッションの全OHLCへ同じように適用される場合、高安差 `(U+a)-(D+a)` と同セッション内の売買価格差は変わらない。一方、途中でaが変わる場合や比率調整では、その不変性を仮定できない。この数学上の性質は、実際にその加工が行われたという証拠ではない。

「5ポイントに丸めれば直る」「警告が少ないから無視する」は採用しない。加工を説明できても、調整価格上の仮想約定と実限月での約定可能性は別の問題として残す。

## 4. Roll-risk監査

`roll_risk=false` の生成箇所、既定値、入力列、欠損時の処理をたどる。boolの全falseだけでは、「ロールがなかった」のか「情報が供給されていない」のか識別できない。

既存Bar/エンジンの列を無断で変更せず、研究用の別表に次を保存する。

| フィールド | 内容 |
|---|---|
| `roll_observation_status` | `known` / `unknown`。未供給をfalseへ変換しない |
| `observed_contract_change` | `true` / `false` / `null`。実際の供給根拠があるときだけ設定 |
| `contract_id` | 供給された実限月識別子。取得できない場合null |
| `evidence_source` | 原データ列、供給者の切替表、データ仕様等の識別子 |
| `available_at` | その情報が当時いつ利用可能だったか。不明ならnull |
| `within_session_switch` | `true` / `false` / `null` |
| `scheduled_roll_window` | 別名で保持するカレンダー上の注意期間 |

SQ日・取引最終日はJPX制度に定義があるが、データ供給者のcenter連続系列が実際に切り替わる日時とは同一とは限らない。[S1] 日付だけから実限月を捏造しない。

### カレンダー由来の補助ラベル

供給者の実切替時刻が不足している場合、該当年の制度・営業日で確認した3/6/9/12月のSQ取引日を中心に、前5取引日から後1取引日までを `scheduled_roll_window=true` とする。この幅は診断用に事前固定し、最も成績が良くなる幅を選ばない。

これは注意期間の**代用ラベル**であり、実ロールの観測値ではない。主戦略の売買フィルターには使わない。暦月による代用ラベルが作れても `unknown` を `known` に変更しない。限月の種類や連続系列の仕様がこの診断と合わない場合は不適用として理由を記録する。

切替日付やセッション内の同一系列性を、供給者の仕様・切替表・実限月データなどで裏付けられない場合、Developmentの限定評価にとどめ、OOS/CANDIDATEへの昇格を止める。

## 5. 重複・欠損・時間定義

完全一致重複は、既存の `05_data_overlap.md` の規約を維持する。全Bar列が一致する重複だけを1本化し、行数・出所を保存する。経済列が一致していても品質フラグが異なるケースを黙って同一扱いしない。

欠損は、カレンダーの予定時刻と正規化バーの差分で判定する。休場とデータ欠落を分ける。初動有効性と、その後の探索・保有・決済時間帯の欠損を別々に報告する。

立会時間は既存の版管理を使用し、JPXの現行時刻を2021年からの全期間に当てない。JPXの現行ページは現行制度の確認に使い、過去変更の適用日は既存calendar設定の根拠と照合する。[S2]

Nightのcalendar_dateとtrade_dateの対応、年末年始、祝日取引、制度変更日の予定開始を合成データで検証する。予定がない日は「欠損セッション」と数えない。

統計的価格ジャンプのフラグも、真の相場変動かデータ問題かを分ける。将来の全期間分布を使って作られたフラグは、当時の売買選択に使わない。既存 `is_eligible` に既に先読みが混入している場合は基盤の品質問題として記録する。

## 6. 品質判定と許可範囲

| `quality_status` | 条件 | 許可する作業 |
|---|---|---|
| `BLOCKED` | 価格変換の原因不明、入力期間漏洩、相違重複、重大な計測不一致等 | 文書・合成テストのみ。実データPnLなし |
| `PASS_LIMITED` | 価格差/初動幅の研究計算は説明できるが、実切替や約定価格対応に未解決点がある | Developmentのみ。必ず暫定結果と表記 |
| `PASS_RESEARCH` | 上記を解決し、対象期間の系列構成・切替影響・価格解釈を証跡で説明できる | Development。別途全ゲート通過後のみOOS |

`PASS_RESEARCH` は本番約定や流動性を保証しない。実限月での再現・運用リスク管理は別途必要。

後半の価格や取引結果を調べた後で、そのセッションを最初から除外した主成績に置き換えない。事後的品質ラベルによる除外結果を出す場合は、「事後的な台帳感度・取引可能ルールではない」と明示し、全件の主成績を残す。

データ修正が必要な場合、rawは不変、既存Gold/結果も上書きせず新バージョンを作る。修正原因、差分、影響するR001/R002結果、PnL回帰テストを記録する。修正後データで旧実験を再確認しても、旧ファイルを消さない。

完了とは、すべての懸念を消すことではなく、どの範囲の研究を許可できるかを根拠付きで確定すること。`PASS_LIMITED` や `BLOCKED` も正当な監査結果である。
