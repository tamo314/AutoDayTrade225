# 128. 範囲完了まで再設計・修正・実行を自動継続する

改訂: **ORCHESTRATION-20260916-02** / 2026-09-16 JST

ユーザーの自動継続依頼を受け、schema_version=2の準備研究ループを追加した。研究範囲は固定し、その範囲の未完了事項を自動で処理する。HOLDや文書作成だけで終了させず、式の訂正・設計の整合化・根拠調査・検証失敗の修正を継続する。

## 1. 開始・再開

プロジェクトrootで実行する。

```powershell
.venv/Scripts/python.exe orchestrator.py --check
.venv/Scripts/python.exe orchestrator.py
```

既定は [C02出来高入力監査バッチ](../../config/orchestration/c02_volume_input_audit.json)。その範囲・完了条件は [132 C02出来高入力監査](132_c02_volume_input_audit.md) を参照する。同じコマンドで保存された工程から再開する。`--once`は利用者が途中で区切る場合だけ使う。状態確認は `--status`。

元のC01タスクはDONE/HOLDの記録を保持し、新しい準備タスクへ参照として継承した。新タスクは旧成果物を修正せず、新出力先に訂正を残す。旧状態は次で参照できる。コードやconfig更新後の過去DONEは `contract_matches_current=false` と表示できるが、この表示は旧タスクの再実行を許可しない。

```powershell
.venv/Scripts/python.exe orchestrator.py --batch config/orchestration/c01_design.json --status
```

`--reset`や状態ファイルの削除は使わない。処理中断・二重起動・ログ保存の基本は [126](126_bounded_orchestration.md) を継承する。

## 2. 自動継続する条件

```text
Executor: 調査・設計・訂正
    ↓
固定validator: 許可された検証の実行
    ↓
Planner: 完了条件ごとの証拠と残作業をレビュー
    ├─ 修正可能な不足 → 再設計・修正指示 → Executor
    ├─ 全条件完了＋検証PASS → 最終監査 → DONE
    └─ 証拠付きの重大障害 → BLOCKED（未完了として記録）
```

- Plannerがdoneと答えても、完了条件の不足、成果物欠落、検証失敗、未完了項目があれば修正へ戻す。
- 最終監査はもう一度Plannerを呼び、同じ成果物の矛盾・不足を能動的に確認する。そこで欠陥が出た場合も自動修正へ戻る。最終監査は同じモデルによる別呼出しであり、独立した専門家の保証ではない。
- HOLD/REJECTは研究判断、DONEは明示範囲の完了。研究判断がHOLDでも範囲内に修正可能な仕事があればcontinue。反対に収益性が示せなくても、指定した研究を全て完了したならDONEにできる。
- 暫定案は理由と履歴を残して修正できる。損益を見た閾値救済、未登録の仮説・対照・市場入力の追加は許可しない。
- 一時的なPlanner失敗・不正形式応答は自動再試行する。Executorを再実行せず、保存済み結果のレビューだけをやり直す。
- 準備タスクのExecutor失敗は、部分成果物と失敗理由をPlannerへ渡して、対処を決めてから再実行する。失敗も呼出履歴へ残す。

## 3. 止める条件

重大障害は、必須情報の回収不能、許可範囲を越えないと進められない依存、権限・資源の障害、必須要件の矛盾など。Plannerは障害の種類・説明・証拠ファイル・試した対処・未完了項目を構造化して返す。単に「HOLD」「値が未指定」だけの停止は受け付けない。対処は実際に行った内容を記録する。

機械側も、保護入力の変更、同じ役割の連続失敗3回、成果物が変わらない修正サイクル3回を継続不能の疑いとしてBLOCKEDにする。最後のケースは初回の比較基準を保存した後に数える。これは完了ではなく、試行・不足を保全した異常停止である。

停滞検出は成果物hashによる近似で、内容上の進捗を完全には判定しない。各サイクルで実際の調査・訂正を成果物に残し、表面的な書換えを進捗としない。エージェントは境界外の操作を避ける必要があり、この仕組みはOSレベルのアクセス隔離ではない。

Ctrl+Cは利用者による中断として尊重する。Planner中断なら保存済みExecutor結果からレビューを再開できる。Executorの中断・親プロセスの異常終了では、子の終了と部分成果物を確認し、無条件に二重実行しない。

Executor timeoutも、子プロセスの終了状態を確認する必要があるため自動再試行せずBLOCKEDにする。終了コードが確定した通常のエラーと区別し、ログと部分成果物を保全する。

## 4. 呼出回数と研究予算を分離する

今回のschema v2では `max_executor_calls=null`、`max_planner_calls=null` とし、旧3/5回で作業を打ち切らない。利用者が明示的な資源上限を設定した場合は、その上限で未完了停止する。すべての呼出回数・失敗は累積する。

この変更は、経済仮説の有限枠、実データattempt、閉鎖family、OOS/Final Holdout保護を変更しない。現在の対象はC01一案の準備で、実データattemptは0件、grantは0件。研究用の値や証拠が未指定でも、関係しない準備作業は進める。実データの実行には引き続き123の凍結manifest・ReviewReceipt・一致grant・残枠が必要。

schema v2はdesignモードだけに適用する。登録済み実データ実行はschema v1の `registered` 経路から一つの凍結manifestを実行・照合する。失敗した市場実験をこの自動修正ループが勝手に再実行することはない。

## 5. 今回の受入条件

C01後続タスクには会計、工程別要件、機構調査、公式カレンダー、準備設計、検証の6条件を設定した。対応する証拠は宣言した4成果物を指定する。ファイルの存在だけを完了根拠にしない。

固定の `scripts/validate_c01_preparation.py` は、二重スリッページ控除、準備作業への資本/DD・family再開の不要な前提、カレンダー構造・全日付網羅、合成会計、祝日＋週末の群優先規則を検査する。これは公的資料の真偽や方向継続の証拠を認定する検証ではない。資料の実読・引用との一致・trade_date対応はPlannerの監査対象である。

実装検証には、旧上限を越える自動継続、検証失敗・不完全doneの差戻し、一時障害からの復帰、最終監査からの再修正、重大障害・停滞による未完了停止、旧DONE参照と再実行拒否を含める。実モデルによる準備研究・実データ研究は実装検証として起動しない。
